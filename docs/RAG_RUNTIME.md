# 직접 실행하는 RAG 경로

추가 정리: [도메인 가정 점검](DOMAIN_ASSUMPTIONS_AUDIT.md),
[ADR-075](ADR/075-explicit-domain-independent-runtime.md). 출처 접미사 검사를
명시적/원문 근거 출처 제약으로 바꾸었고, 모델·비용·근거 한도 설정을 노출했다.
`--required-source`는 반복 지정 가능하다. `--model`로 다른 모델을 선택하면
`--input-usd-per-million`, `--output-usd-per-million`도 함께 지정한다.
`--max-documents`, `--max-cells-per-document`, `--limit`로 기본 한도를 바꾼다.

현재 사용자 질의 경로는 `rag`다. `retrieval_experiment`의 A/B/C/D,
재무 전용 `parse_question()`, 고정 코퍼스 Tree 조회는 활성 소스에서 제거했다.
기본 검색은 PostgreSQL FTS + 부분 문자열이며 원본 질문, 행·열 경로와 셀 원문을 사용한다.
`dense`는 pgvector 코사인 검색, `hybrid`는 기존 검색과 벡터 검색의 RRF 결합을 선택한다.
벡터 모드는 pgvector 스키마와 같은 모델 프로필로 생성한 문서 임베딩이 필요하다.

## 준비

- Python 환경 및 기존 로컬 PostgreSQL이 실행 가능해야 한다.
- 질문할 문서의 CanonicalDocument가 DB에 적재되어 있어야 한다.
- 모델 호출 시 환경변수 OPENAI_API_KEY와 `--allow-external`이 필요하다.
- 출력 경로는 매번 새 경로를 사용한다. 아래 질문과 실행 ID는 직접 바꿔 넣는다.
- 이번 정리에서는 DB 연결이나 실제 유료 모델 호출을 실행하지 않았다.

## 웹에서 문서별 검색 준비와 질문

`http://localhost:8766/`에서 문서를 업로드하거나 실행 이력의 완료 결과를 연다.
아래 **이 문서로 검색하고 질문하기** 패널은 선택된 문서에만 적용된다.

1. **검색 항목 보기**를 펼쳐 실제 임베딩 입력 텍스트·유형·페이지·원문 셀·행열 경로를 확인한다.
   문서 JSON의 현재 검색 표현을 미리 보며, 저장된 프로필이 있으면 DB의 입력 해시로 임베딩 상태를 대조한다.
   DB 조회 실패는 미임베딩으로 간주하지 않고 상태 미확인으로 표시한다.
2. 임베딩 공급자를 고른다. 기본은 **OpenAI `text-embedding-3-small`**(1,536차원)이다. 단가 칸에는
   2026-11-10 공식 모델 페이지 기준 $0.02/100만 토큰이 미리 들어가며 실행 전에 다시 확인한다.
   실행 비용 한도와 서버 환경변수 `OPENAI_API_KEY`가 필요하다. 키를 브라우저 입력·로컬 저장소에 보관하지 않는다.
   **로컬(Ollama)**을 고르면 `bge-m3`·1,024차원, 단가 0, 외부 동의·키 없이 실행하며 배치 8개·120초 제한을 쓴다.
3. **검색 준비 · 임베딩**을 실행한다(OpenAI는 외부 전송 동의 후). 원본 검증 → DB 적재·검색 색인 → pgvector 준비 →
   배치 임베딩 순서로 진행한다. **DB 적재만 실행**은 임베딩 없이 키워드 검색을 준비한다.
4. 동일 문서에 질문을 입력하고 키워드·벡터·하이브리드 중 하나를 고른다. 기본은 검색 결과 확인이다.
   **근거로 답변도 생성**을 선택하면 답변 모델·입출력 단가·비용 한도를 적용해 기존 인용 검사를 거친 답변을 표시한다.
   검색 후보·점수·근거 문맥·비용 기록을 펼쳐 비교하고, 원문 보기 버튼으로 해당 페이지·셀에 돌아간다.

업로드는 유료 호출을 시작하지 않는다. 벡터 검색은 질문도 같은 공급자로 임베딩하고, 답변 생성은 별도 모델을 호출한다.
로컬 임베딩만 쓰는 검색은 외부 전송·비용이 없다. 근거로 답변 생성은 여전히 OpenAI 호출과 동의가 필요하다.
모든 비용 한도는 요청별이며 임베딩과 답변 한도는 별개다. 같은 질문을 다시 실행해도 새 호출 비용이 발생할 수 있다.
벡터가 없을 때 하이브리드가 키워드 검색만 사용한 사실도 표시한다. 검색·답변 완료를 정답 승인으로 해석하지 않는다.

`services/web_rag.py`는 기존 RAG 모듈을 호출하며, `web/rag_routes.py`는 완료 문서·요청 토큰을 검사한다.
`work/web-rag/<job-id>/`에 요청별 상태·설정·진행률·감사 기록을 보존한다. 파서의 기존 결과는 수정하지 않는다.
원본 manifest를 찾을 수 없는 과거 문서는 재업로드가 필요하다. 원본이나 색인 버전이 바뀌면 다시 검색 준비해야 한다.
실행 중 중복 요청은 막고 같은 요청 ID는 재실행하지 않는다. 실패 후 새 요청은 완료된 벡터를 해시로 재사용한다.
재시작으로 중단된 작업은 `interrupted`로 남기고 자동으로 유료 호출을 재개하지 않는다.
단일 Uvicorn 프로세스·한 작업 실행을 전제로 하며 다중 worker의 분산 잠금은 제공하지 않는다.

## 문서 코퍼스 질문 화면 (`/ask`)

`http://localhost:8766/ask`는 적재된 문서 전체를 하나의 검색 대상(코퍼스)으로 다룬다.

- **코퍼스:** 문서(PDF 해시)마다 최신 완료 실행 하나만 쓴다. 현재 색인 버전이 아니면 "재색인 필요"로만
  보여 주고 검색하지 않는다. 같은 문서를 여러 번 적재해도 결과가 중복되지 않는다.
- **적재:** 분석이 끝난 문서를 골라 구조 검토 → DB 적재·색인 → 임베딩을 문서마다 차례로 실행한다.
  다른 실행에 같은 프로필·같은 입력 원문의 벡터가 있으면 복사하므로 다시 임베딩하지 않는다. 문서별
  결과(새 임베딩·복사 수, 실패 이유)를 남기며 한 문서가 실패해도 나머지는 계속한다.
- **질문:** 문서를 고르지 않으면 전체에서 검색한다(기본). 이때 화면은 문서 ID를 보내지 않고 서버가
  "현재 색인 버전의 최신 실행 전체"를 SQL 조건으로 거른다(`rag/retrieval/scope.py`의 `CorpusScope` — 실행 ID를
  나열하지 않는다). 특정 문서로 좁히려면 "특정 문서로 좁히기"에서 이름으로 찾아 고른다(최대 200개).
  질문 이해 에이전트·답변 방식·모델 설정은 문서별 패널과 같고 근거는 최대 3개 문서에서 모은다. 질문 기록이
  화면에 쌓이고 근거마다 원문 화면 링크가 있다(문서 이름·링크는 근거에 나온 문서에 한해 작업 기록에 싣는다).
- **문서 목록표(`rag/catalog.py`, 표 `rag.document_catalog`):** 색인된 실행마다 한 줄(이름·쪽수·표 수·검색 항목 수·
  구조 검토 적용 여부·현재 검색 대상 여부). 색인 트랜잭션에서 함께 쓰고, 목록 조회·검색 범위·질문 처리는 이 표만
  읽는다(문서 저장본을 열지 않는다). 화면은 코퍼스 규모 요약(문서·쪽·표·검색 항목·임베딩 수)만 받고 문서를 전부
  나열하지 않는다. 표가 생기기 전의 실행은 프로세스의 첫 조회 때 한 번 채운다.
- 웹 RAG 작업과 같은 큐를 써서 한 번에 한 작업만 실행한다. 상태는 `work/web-rag/corpus/`에 남는다.

답변 표시: 화면 경로는 선택형 응답에 `answer_text`(짧은 답변 문장)와 `alternatives`(다른 해석과 그 근거 ID)를
함께 받는다(추가 호출 없음). 문장에 선택 값이 그대로 들어 있고 숫자가 선택 근거·질문에 있을 때만 모델 문장을
쓰고, 아니면 근거 값으로 만든 문장으로 대체한다(`answer_text_source`). 다른 해석은 근거 ID가 실제로 있을 때만
보인다. 여러 줄 셀에서는 한 줄 전체가 정확히 같을 때만 그 줄을 답 값으로 인정한다. 화면은 답변 / 답변에 쓴 근거 /
검색된 다른 근거(접힘)로 나뉜다.

API: `GET /api/rag/corpus`(규모 요약과 적재할 작업 상태), `GET /api/rag/corpus/documents?q=&limit=&offset=&stale=`
(이름으로 찾은 문서 한 쪽 분량), `GET /api/rag/corpus/state`, `POST /api/rag/corpus/ingest`,
`POST /api/rag/corpus/question`(쓰기 요청은 화면 토큰 필요. `run_ids`를 비우면 전체 검색).

2026-11-12 확인(문서 37개·쪽 251·검색 항목 11,283): 문서 목록 조회 1.17초 → 0.003초(목록표), 목록표 내용은 예전
조회 결과와 37줄 모두 같음. 개발용 45문항에서 실행 ID 나열과 코퍼스 범위의 검색 후보·근거가 모두 같음(질문
임베딩을 고정했을 때. 임베딩 API를 다시 부르면 벡터가 미세하게 달라 동점 순위가 바뀌는 문항이 있었다 — 4/45).

2026-11-10 실제 실행 관찰(질문 1개): 답변 모델의 출처 형식 실수가 검사에 걸려 보류되는 일이 있었다.
gpt-4.1-mini는 행 경로 두 라벨을 이어 인용해 보류됐고, gpt-4.1은 형식을 지켰다(문맥 출처를 답변 값에
넣은 실수는 결정적으로 덜어낸다). 정확도 비교는 평가셋으로 다시 해야 한다.

## 검색·답변 화면 (`/search`)

`http://localhost:8766/search`는 문서를 고르지 않고 검색 가능한 전체 문서에서 질문하고, 답변의 인용 근거를 원문과
대조하는 사용자용 화면이다. 질문·적재·문서 찾기는 `/ask`와 같은 코퍼스 API를 쓰고, 근거 검사도 같다.

- 접속하면 질문 입력창과 지금 검색 가능한 문서 수가 보인다. 범위를 좁히려면 문서 이름으로 찾아 고른다(선택).
- 처리 중에는 실제로 들어간 단계만 보인다: 질문 이해 → 검색 → 근거 준비 → 근거 선별 → 답변 생성(근거가 부족하면
  한 번 더 검색). 단계는 에이전트가 알리는 값이다(`rag/agentic/run.py`의 `progress`).
- 결과는 네 가지로 구분한다: 답변(인용 근거 포함), 답변 보류(근거는 찾았으나 확정하지 못함), 검색 근거 없음, 처리
  오류(실행 실패). 인용 근거에는 문서 이름·쪽·인용 원문이 보이고, 행·열 경로와 문맥(적용 범위·단위·주석·담긴 위치)은
  펼쳐서 본다. 실행 ID·색인 버전·비용은 '상세 정보' 안에만 있다.
- 인용을 누르면 오른쪽 원문 패널에 그 문서의 쪽이 열린다.
  - PDF: 쪽 그림 위에 근거 영역을 표시한다. 표 근거는 아래에 표 격자가 나오고 인용 칸과 같은 행·열이 표시된다
    (큰 표는 인용 칸 주변과 머리글만, '표 전체 보기' 가능). 격자의 칸을 누르면 원문에서 그 칸 위치를 따로 표시한다.
    본문 근거는 앞뒤 두 문단씩 보여 준다.
  - HTML: 격리된 틀(스크립트·외부 요청 차단)에 원문을 보여 준다. 쪽 좌표가 없으므로 위치를 표시하지 않는다.
  - 좌표를 쓰는 조건: 원본이 PDF이고, 색인에 저장된 쪽 크기가 지금 파일의 쪽 크기와 같다(1% 이내). 아니면 쪽만
    보여 주고 이유를 적는다(추정한 위치를 정확한 위치처럼 표시하지 않는다).
  - 원본 파일을 찾지 못하면 그 상태를 알리고, 색인에 저장된 인용 문구와 표만 보여 준다.
- 원본 파일은 적재 경로와 무관하게 문서 ID(내용 해시)로 `data/`와 화면 작업 폴더에서 찾는다
  (`services/source_view.py`). 표 격자와 쪽 크기는 색인한 문서 저장본에서 그 표·그 쪽만 꺼낸다.
- 문서 추가: 파일을 올리면 ① 분석 → ② 검색 준비(구조 검토 → 색인 → 임베딩) 순서로 진행한다. ②가 '검색 가능'이
  되어야 질문에 쓰인다. 색인만 끝나고 임베딩이 덜 된 문서는 '키워드로만 검색됨'으로 따로 표시한다. 적재와 질문은
  서로 다른 줄에서 실행하므로 준비 중에도 질문할 수 있다. 다시 시도해도 문서가 중복으로 쌓이지 않고(문서마다 최신
  실행 하나만 검색), 같은 문구의 임베딩은 다시 받지 않는다.
- 문제 기록: 답변마다 '답변 오류·근거 누락·잘못된 인용'과 의견을 남길 수 있다. 실패 장부에 `kind=feedback`으로
  덧붙고 `work/feedback/<의견 ID>/failures.json`에 질문·답변·실행·인용 근거와 함께 저장된다. 검토 전 의견이며
  (`review.status=unreviewed`) 정답 데이터나 분석 결과를 자동으로 바꾸지 않는다.

화면 구성(2026-11-12 디자인 개편): 위쪽 탭으로 '질문'과 '문서'를 오간다.
- 질문: 왼쪽에 질문과 답변, 오른쪽에 원문 패널(인용을 누르면 열림).
- 문서: 검색 가능한 문서 목록(12개씩 쪽 번호로 이동, 이름 찾기). 문서를 누르면 문서 보기 팝업이 뜨고, 양옆 버튼·
  좌우 화살표 키·쪽 번호 입력으로 쪽을 넘긴다. HTML 문서는 원문 전체를 보여 준다.
- 문서 추가: 오른쪽 위 '문서 추가' 버튼의 팝업에서 올린다. 팝업을 닫아도 처리 중이면 버튼에 점이 표시된다.

화면 파일은 `web/static/search/` 아래에 기능별로 나뉜다(빌드 과정 없음, 브라우저 모듈).
- `index.html`: 뼈대와 아이콘.
- `css/`: `tokens`(색·글꼴·간격 기준, 밝은·어두운 화면) → `base`(버튼·입력·상태 표시) → `layout`(머리·탭) → `answer` →
  `viewer` → `documents` → `dialogs` → `responsive`(화면 폭 대응, 맨 마지막에 불러온다).
- `js/`: `main`(시작점·탭), `dom`·`api`·`config`(공용), `status`, `scope`·`ask`·`answer`·`feedback`(질문과 답변),
  `viewer`·`grid`·`evidence`(원문 패널), `documents`·`reader`(문서 목록과 문서 보기), `uploads`(문서 추가).
- 디자인 규칙: 강조색은 하나, 노란색은 인용 근거 표시 전용, 모서리는 조작 요소 8px·면 12px, 색은 `tokens.css`의
  변수로만 쓴다. 글꼴(Pretendard)은 외부에서 받아 오며, 받지 못하면 시스템 글꼴로 동작한다.

API: `GET /api/search/status`, `GET /api/search/source?run_id=&page=`, `GET /api/search/source/page?run_id=&number=`,
`GET /api/search/source/html?run_id=`, `GET /api/search/table?run_id=&table_id=`,
`GET /api/search/context?run_id=&content_id=`, `GET /api/search/uploads?ids=`, `POST·GET /api/search/feedback`,
`GET /api/rag/corpus/tasks/{request_id}`(질문·적재 한 건의 진행 상태).

## 검색 후보부터 확인

```powershell
.venv/Scripts/python.exe -X utf8 -m doc_understanding.rag search --question "직접 입력한 질문" --run-id "저장된 실행 ID" --output "work/manual-rag/search-01.json"
```

`--run-id`를 생략하면 저장된 문서들의 최신 완료 실행에서 검색한다.
이 명령은 모델을 호출하지 않는다. 표/행/본문 후보, 점수와 원문 연결 ID를 확인한다.

## 전체 흐름 확인

```powershell
.venv/Scripts/python.exe -X utf8 -m doc_understanding.rag ask --question "직접 입력한 질문" --run-id "저장된 실행 ID" --output "work/manual-rag/run-01" --allow-external
```

기본은 질문 그대로 검색해 한 번 답한다. `--planner`를 추가하면 화면과 같은 질문 에이전트 그래프로 실행한다(아래).
`--answer-mode narrative`는 문장형 답변을 선택한다.

### 질문 에이전트 그래프

화면(`/search`, `/ask`), 평가(`scripts/evaluate_rag.py`), `ask --planner`는 같은 LangGraph 그래프를 쓴다.
실행 순서와 분기는 `rag/agentic/graph.py`에만 있고, 각 노드가 하는 일은 `rag/agentic/run.py`에 있다.

```text
START → plan_question → select_documents ─┬→ gather_evidence → select_evidence ─┬─────────────→ generate_answer → END
                                          │        ↑                           └→ expand_evidence ─↗      │
                                          │        │                                   ↑                  │
                                          │        │                                   └ 보류했고 아직 넓히지 않았으면 ┤
                                          │        └────────── 근거가 부족한 질문 구간이 있으면 한 번만 ──────────────┘
                                          └→ END (되묻기, 해당 문서 없음: 검색·답변을 하지 않는다)

select_evidence → read_grid → END (비교할 문서들의 필수 행을 원문 격자에서 직접 읽어야 할 때)
```

| 노드 | 하는 일 | 화면 단계 |
|---|---|---|
| plan_question | 질문을 요구 사항과 검색어로 나눈다(모델 1회, 실패하면 질문 원문으로 대체) | 질문 이해 |
| select_documents | 질문이 가리킨 대상을 문서 메타데이터와 맞춰 검색할 문서를 정한다(`rag/agentic/documents.py`) | 문서 고르기 |
| gather_evidence | 검색어별 검색, 표 구조 일치, 문맥 보충 | 검색, 근거 준비 |
| select_evidence | 리랭커로 근거를 추려 E1..로 번호를 다시 매긴다(리랭커가 없으면 그대로) | 근거 선별 |
| expand_evidence | 선별된 근거가 속한 표의 칸을 모두 근거로 넣는다(`rag/agentic/reading.py`) | 표 전체 읽기 |
| generate_answer | 답변과 근거 판단을 만들고 검사한다. 근거가 없으면 모델을 부르지 않는다 | 답변 생성 |
| read_grid | 보류 뒤 또는 비교에 필요한 행이 구조 미확정 표에만 있을 때 원문 격자를 한 번 읽힌다 | 표 원문 읽기 |

재검색은 답변 검사에서 "근거 부족"으로 판정된 질문 구간을 검색어에 더해 한 번만 한다. 자동 반복은 없다.

비교할 문서들에서 질문에 명시한 같은 행을 찾았지만 모두 구조가 미확정이면,
`select_evidence`가 `required_grid_rows`와 읽을 표를 지정하면 그래프는 `read_grid`로 바로 보낸다.
이 경로는 일반 답변과 표 전체 확장보다 먼저 실행하고 곧바로 끝난다. 격자 읽기가 실패하거나
인용 검사를 통과하지 못하면 기존 보류를 유지하며, 자동 재시도하지 않는다.

**질문의 조건 확인.** 계획 모델은 같은 표현에서 답이 달라지는 해석이 둘 이상이면 질문 원문 구간, 가능한 해석과 확인 질문을 남긴다.
에이전트는 검색 전에 확인 질문을 보여 준다(`result.clarification.kind = needs_context`). 대상이 생략됐고 검색 범위에 문서가 여럿이면 문서도 묻는다.
개발 평가셋 `config/evaluation/rag-maturity-paired-dev-v1.json`은 기존 네 문항과 수협 명시 문항을 함께 검사한다.
`rag/4-grounded-ambiguity`에서는 단순 보류는 실패다. 되묻기는 지정된 쟁점을 포함해야 하고, 조건부 답은 가정·값과 그 해석에 해당하는 원문 위치를 함께 확인한다.

**문서 고르기.** 같은 양식의 문서가 기관만 바꿔 여러 벌 있으면 전체에서 그냥 찾을 때 다른 기관 문서의 값이 섞인다.
그래서 계획 모델이 질문이 가리킨 대상(기관·상품·문서 이름)을 질문 문구 그대로 뽑고(`plan.subjects`, 최대 3개),
코드가 그 문구를 문서의 이름들(메타데이터의 기관·문서 이름·다른 표기, 표시 이름, 파일 이름)과 글자로 맞춘다. 모델 호출은
늘지 않는다. 비교 전에 전각·반각, 대소문자, 공백·기호 차이를 없앤다. 낱말 뜻이나 특정 기관 이름에 따른 규칙은 없다.

| 맞춘 결과 | 처리 |
|---|---|
| 대상의 모든 낱말을 강한 이름으로 덮는 문서가 1개 | 그 문서 안에서만 검색 |
| 그런 문서가 2~5개 | 되묻는다(`result.clarification.kind = needs_choice`). 검색·답변 호출 없음 |
| 그런 문서가 6개 이상 | 그 문서들 안에서만 검색 |
| 모델이 추정한 표기나 한 글자 차이(5글자 이상)로만 맞음, 일부 낱말만 맞음, 본문에만 나옴 | 좁히지 않고 전체 검색. 답한 뒤 인용한 문서가 대상을 언급하는지 확인하고, 아니면 보류(`subject_check`) |
| 대상의 낱말이 어느 문서 이름에도 본문에도 없음 | "해당 문서 없음"(`document_missing`). 검색·답변 호출 없음 |
| 대상 없음 | 전체 검색 |

두 글자 이하 낱말은 이름 낱말과 같거나 그 앞·뒤에 붙어 있을 때만 맞은 것으로 본다. 사용자가 화면에서 문서를 직접 고른
질문은 고르기를 하지 않는다. 범위가 표 15개 이하인 문서 하나로 정해지면 그 문서의 표를 모두 구조 일치 후보에 넣는다
(검색은 라벨의 띄어쓰기 차이로 맞는 표를 놓칠 수 있다). 구조 일치 점수가 같으면 요구 문구와 라벨이 똑같은 칸이 앞선다.
고른 결과는 `agent-run.json`의 `documents`와 화면의 "찾은 문서"에 남는다. 화면의 되묻기 카드에서 문서를 누르면 같은
질문을 그 문서 범위로 다시 보낸다. 문서 목록은 지금 한 번에 모두 읽는다(`rag/agentic/directory.py`). 문서가 수만 개면
이름 맞춤을 SQL로 옮겨야 한다.

**원문 격자 읽기.** 구조 해석이 표 전체를 보류한 표(쓸 수 있는 칸 0)는 검색에는 걸리지만 근거로 복원되지 않는다.
답이 보류로 끝났고 그런 표가 검색에 걸렸으면, 재검색과 표 전체 넓히기 뒤의 마지막 시도로 그 표의 물리 격자를 모델에
읽힌다(`read_grid` 노드, `rag/agentic/grid.py`, 화면 단계 "표 원문 읽기"). 질문 이해 모델과 같은 작은 모델을 쓰고 질문 한
건에 한 번이다. 읽은 결과는 구조로 저장하지 않는다.

- 주는 것: 칸마다 위치(행·열), 병합 범위, 글자. 머리글이나 행 라벨이 어디인지는 주지 않는다. 후보 표가 여럿이면 질문과
  글자가 가장 잘 맞는 표 2개까지(칸 글자 합 12,000자 이내) 읽힌다. 칸당 평균 글자가 1.5자 미만인 격자(그래프 눈금, 빈
  양식)는 보내지 않는다. 바로 앞쪽들에 열 수가 같은 표가 이어져 있으면 맨 앞 표의 첫 행을 머리글 후보로 함께 준다.
- 받는 것: 답이 적힌 칸, 그 칸을 가리키는 행 라벨 칸과 열 라벨 칸, 한 문장 답.
- 검사: 칸이 실제로 있는가, 답 칸에 글자가 있는가, 라벨 칸을 하나 이상 댔는가, 라벨 칸이 답 칸과 같은 행·열에 있는가,
  숫자만으로 된 라벨이 질문에 나온 숫자인가, 답 문장의 숫자가 인용한 칸에 있는가. 하나라도 어기면 앞의 보류를 그대로 둔다.
- 결과: `generation_mode = raw_grid_reading`. 근거 칸은 `lookup_eligible = false`(경로 미확정)로 두고, 화면은 "구조가
  확정되지 않은 표를 읽은 답"이라고 알린다. 기록은 `agent-run.json`의 `attempts[].trace.grid`.
- 남는 위험: 여러 단 머리글에서 옆 열의 값을 고르는 오답, 같은 항목이 여러 쪽의 표에 있을 때 다른 쪽의 값을 고르는 오답은
  이 검사로 걸러지지 않는다. 긴 목록에서 행 번호로 찾는 질문은 검색이 그 쪽의 표를 가져오지 못하면 답하지 못한다.

**읽기 범위 분기.** 선별은 질문과 가장 가까운 근거 12개만 남긴다. 값 하나를 찾는 질문에는 충분하지만 표 전체를
봐야 하는 질문(전부 나열, 조건을 대입한 판단, 비교)은 나머지 행 없이 답하게 된다. 그래서 두 경우에 근거가 속한 표를
통째로 넣는다.

1. 계획 모델이 `reading: "whole"`이라고 한 질문: 답하기 전에 넓힌다. 판단은 계획 모델이 하고, 코드에는 질문 낱말이나
   문서 종류에 따른 규칙이 없다.
2. 선별된 근거로 답했는데 보류가 나온 질문: 질문 한 건에 한 번만 넓혀서 다시 답한다(계획의 판단이 틀린 경우의 안전장치).
   넓혀도 더해지는 칸이 없으면 답변 모델을 다시 부르지 않는다.

넓힐 때의 한계: 칸이 150개를 넘는 표는 넓히지 않고, 넓힌 근거 원문이 약 36KB를 넘으면 뒤 순위 표부터 넓히지 않는다
(표를 잘라 일부만 넣지 않는다). 넓힌 요청이 답변 요청 한도를 넘으면 넓히기 전 근거로 답하고 기록에
`REQUEST_TOO_LARGE`를 남긴다. 본문 근거는 넓히지 않는다(쪽·절 단위 넓히기는 아직 없다). 넓힌 기록은
`agent-run.json`의 `attempts[].trace.reading`에 있다. 답변 모델 호출은 질문 한 건에 많아야 세 번이다.

표에 경로가 확정되지 않아 근거로 쓸 수 없는 칸이 있으면 그 칸은 넣지 않고 수를 기록한다(`withheld`). 전체를 읽어야
하는 질문인데 표를 통째로 읽지 못했거나 빠진 칸이 있으면 결과에 `reading_incomplete`를 남기고, 화면은 "일부만 답했을 수
있습니다"라고 알린다.

**출처 문서 이름표.** 답변 요청의 출처마다 문서 표시(`doc`: D1, D2 …)를 붙이고, `documents`에 문서별 이름표(파일 이름 +
첫 쪽 제목, `rag/evidence/document.py`)를 한 번씩 싣는다. 화면에서 올린 문서는 파일 이름이 모두 `input.pdf`라 이름표가
없으면 모델이 어느 기관·상품의 값인지 알 수 없다. 지시문은 질문이 가리킨 대상과 다른 문서의 값으로 답하지 말라고 하지만,
코드로 강제하는 검사는 아직 없다(2026-11-13 측정에서 다른 농협 문서의 값을 답한 사례가 1건 남았다).

**문서 메타데이터.** 문서마다 기관·문서 이름·문서 종류·기준 시점·다른 표기·한 줄 설명을 저장한다
(`rag.document_metadata`, 문서 ID 기준이라 다시 적재해도 남는다). 적재할 때 색인 뒤·임베딩 앞에서 모델을 한 번 불러
뽑는다(요청의 `metadata: true`, 구조 검토와 같은 모델·단가, 앞쪽 두 쪽의 글만 보낸다. `rag/metadata/extract.py`).
기관·이름·종류·기준 시점은 인용 문구가 그 쪽 원문에 있고 값이 인용의 일부일 때만 남긴다. 다른 표기는 원문에 없을 수
있어 `model_unverified`로 표시한다. 사람이 고친 값은 따로 저장되어 모델 값보다 우선하고 다시 뽑아도 지워지지 않는다
(`rag/metadata/store.py`). 추출이 실패해도 검색 준비는 계속한다. 이미 적재된 문서는
`scripts/extract_metadata.py`로 뽑는다(`--show`는 저장된 값을 표로 보여 준다). 값은 사람 검증 전 후보다.
2026-11-13에 112개 문서를 뽑았다(실패 0, 약 0.16달러). 기관이 비어 있는 문서 16개, 문서 이름이 비어 있는 문서 4개,
기관이 상품 이름이나 일반 명칭으로 잘못 뽑힌 문서가 8개쯤 있다(예: `하나`, `KDBpension`, `저축은행`). 아직 문서 고르기에는
쓰지 않는다.

**같은 질문에는 같은 답.** 계획 모델은 온도 0에서도 검색어를 실행마다 조금씩 다르게 낸다. 검사를 통과한 계획은
질문 문구·모델·지시문별로 보관해 다시 쓴다(화면: `work/web-rag/plan-cache`, 평가: `work/rag-eval/plan-cache`).
답변 호출도 계획·선별 호출처럼 온도 0으로 보낸다.

**답변 문장 검사.** 화면의 답변 문장은 모델이 쓴 문장을 검사해 쓰고, 검사에 걸리면 근거 칸 원문을 이어 붙인 문장으로
바꾼다(`generation/answer.py`의 `present`). 문장은 모델이 직접 고른 값을 담아야 한다: 짧은 값은 그대로, 30자를 넘는 값
(약관 조문, 설명문)은 그 값의 숫자 하나나 이어진 6자 이상(`said`). 문장의 숫자는 고른 근거의 값·경로나 질문에 있는
숫자여야 하며, 쉼표 표기만 다른 숫자는 같은 숫자로 본다.

**판단 근거와 인용.** 답변 모델이 판단에 쓴 근거(예: 어느 상품 문서인지 확인한 줄)를 답변 값으로 고르지 않았으면,
예전에는 답 전체를 버렸다(`ASSESSMENT_OUTSIDE_SELECTED_EVIDENCE`). 지금은 그 근거를 인용 목록에 더해 화면에 함께
보여 준다(`generation/answer.py`의 `include_assessed`). 인용 문구가 출처 원문에 있는지, 조회 가능한 근거인지 등
나머지 검사는 그대로이고, 보류를 답으로 바꾸지 않는다.
옛 그래프(`rag/graph.py`)와 `scripts/run_langgraph_rag.py`, 그 전용 질문 해석(`generation/understanding.py`)은
어디에서도 쓰이지 않아 2026-11-13에 삭제했다.
`--langfuse-config`는 사용자가 선택한 연결 설정으로 추적을 추가하는 옵션이다.
저장 응답 재생, 가짜 키 주입, 과거 RAG 비교 옵션은 없다.

| 단계 | 코드 | 확인할 결과 |
|---|---|---|
| 질문 계획(에이전트) | rag/agentic/graph.py, agentic/run.py, agentic/plan.py | agent-run.json의 plan, plan_check |
| FTS·부분문자열 검색 | rag/retrieval/repository.py, retrieval/lexical.py | candidates, search_request |

| 근거 형식·출처 사전 검사 | rag/evidence/validation.py, evidence/constraints.py, service.py | validation |
| 질문 조건별 판단·원문 연결 검사 | rag/evidence/assessment.py, generation/answer.py, generation/narrative.py | result.assessment_validation, errors |
| 원본 SQL 대조 | rag/retrieval/repository.py | sql-probes.json |

`state.json`에 검색 후보·근거·검증·답변·오류가 저장된다. `summary.json`은 결과 요약,
`graph.mmd`는 그래프 구조다. 모델 호출이 수행된 경우 `graph/` 아래 request.json,
response.json, evidence.json, source-catalog.json, assessment-validation.json, answer.json 등을 확인한다. 근거 없음/검증 보류/실패로
종료하면 일부 파일은 생성되지 않을 수 있다. 오류는 Mock 응답으로 대체하지 않는다.

## 본문·긴 셀의 검색 조각

`indexing/chunking.py`는 같은 원본 블록·페이지·섹션의 연속된 본문 줄만 묶는다.
수직 간격과 가로 겹침을 확인하며 표·주석·제목·읽기 순서 불확실성을 넘지 않는다.
묶음은 최대 2,400자이며 단일 원본 Content 자체가 긴 경우에는 잘라 버리지 않는다.
이는 검색용 문단 후보이고 실제 의미상 문단 경계에 대한 승인은 아니다.

본문과 600자를 넘는 매핑된 셀에는 최대 600자 원문 조각을 만든다. 이 한도는
토큰 수가 아닌 Python 문자열 문자 수이며, 제목·경로·주변 문맥을 붙인 전체 검색
항목 길이의 한도는 아니다. 기존 표 개요·행 검색 항목도 유지한다.
`source_segments`는 원본 Content 또는 셀의 ID, 반열린 문자 범위
`[char_start, char_end)`, 출처 좌표를 보존한다. 본문 결합 줄바꿈은 검색용이며
PDF 원문 인용으로 사용하지 않는다. 문자 범위는 CanonicalDocument 원문 기준이다.

`evidence/projections.py`는 현재 원문에서 검색 항목을 재생성하여 문구·범위·연결을
대조한다. 본문 검색 조각은 묶음에 속한 원본 Content 전체를 각각 복원하고,
셀 검색 조각은 셀 전체를 우선 복원한 뒤 같은 행의 값들을 기존 셀 한도 안에서
선택한다. 같은 문단·셀 내부의 조건을 검색 조각 끝에서 잘라 답변하지 않는다.
본문 출처 목록과 span ID도 유지하며 미해결 매핑의 값 조회 금지는 그대로다.
묶음 밖의 관련 조건, 전체 행의 모든 값 전달, 의미적 완전성까지 보장하는 것은 아니다.
복원된 근거가 모델 입력 한도를 넘으면 기존 예산 검사에 따라 중단하며 몰래 자르지 않는다.

검색 인덱스 버전은 `document-rag/0.9-label-collision`다.

0.9 — 라벨 글자 경로 충돌(`rag/evidence/cells.py`의 `withhold_label_collisions`): 서로 다른 행의 두 값 칸이 같은
(행 라벨 글자, 열 라벨 글자) 경로를 가지면 그 경로로는 칸 하나를 가리킬 수 없으므로 값 조회 근거에서 뺀다
(`lookup_eligible=False`, `path_collision='label_text'`). 행을 가르는 라벨이 경로에서 빠진 경우다(예: 같은 값이
여러 행에 반복되는 첫 열만 행 라벨로 본 2단 행 라벨 표). 분석기의 충돌 검사는 라벨 노드 ID로 비교해 이 경우를
못 본다. 어느 해석이 맞는지는 정하지 않는다 — 틀린 확정을 보류로 바꿀 뿐이고 경로를 맞히지는 않는다.
같은 행의 나란한 값 칸 묶음은 대상이 아니다. 2026-11-12 측정(코퍼스 37문서, 근거로 쓰이던 값 칸 3,956개 중
24개·표 1개가 해당): 매핑 개발 세트 변화 없음(경로 정확 317/317, 틀린 확정 0, 맞는데 보류 0), 검증 세트
틀린 확정 38 → 22·값이 아닌데 근거로 쓰임 10 → 2·경로 정확 0.734 그대로·맞는데 보류 0. 이 규칙은 검증 세트의
실패 유형에서 나왔고 코퍼스에서 해당하는 표가 그 검증 문서의 표 하나뿐이므로, 검증 세트 수치는 독립된 확인이 아니다
(반례는 `tests/test_label_collision.py`의 만든 표로 검사).

0.8 — 근거 저장본(`rag/evidence/source.py`, 표 `rag.evidence_item`): 질문 경로는 문서 전체를 읽지 않는다.
색인을 만들 때 표 하나의 근거 재료(쪽, 적용 범위 후보, 셀 목록: 원문·행열 경로·주석·단위·값 묶음·담긴 위치)와
글자가 있는 본문 내용 하나를 각각 한 행으로 저장하고(검색 항목과 같은 트랜잭션), 질문 때는 검색에 걸린 표·본문만 ID로
읽는다(`repository.evidence_source(run_id)` → `StoredSource`). 구조 일치(`agentic/tools.py`)와 근거 복원
(`evidence/pack.py`)은 문서(`DocumentSource`)와 저장본(`StoredSource`)을 같은 인터페이스로 받으며 결과가 같다.
- 저장본은 색인 버전이 지금 코드와 같을 때만 쓴다. 다르면 `EVIDENCE_STORE_STALE`이며 다시 적재해야 한다.
- 원문 범위를 가진 검색 조각은 근거로 쓰기 전에 색인에 저장된 기준 항목과 대조한다(`SEARCH_PROJECTION_SOURCE_MISMATCH`).
- 점검: `scripts/check_evidence_store.py`(저장본과 문서에서 지금 계산한 것이 같은지 코퍼스 전체 비교, 모델 호출 없음).
  색인 코드를 바꾼 뒤와 재색인 뒤에 돌린다.
- 문서 전체가 필요한 곳(적재, `/mapping`, 평가 스크립트)은 `fetch_document`를 쓰며 최근 문서 4개를 기억한다.
- 측정(코퍼스 11문서, 개발 45문항, 같은 계획·같은 검색 결과): 저장본 근거와 문서 근거가 45문항 모두 같음.
  새 프로세스의 첫 질문 검색·근거 단계 3.5초 → 1.7초(이후 질문은 약 1초로 같음: 남은 시간은 검색 자체).
  저장본 크기는 문서당 최대 1.7MB.

0.7 — 문서 이름표: 모든 검색 항목 맨 앞에 문서 이름표
(`rag/evidence/document.py`: 파일 이름 + 첫 쪽에서 글자가 가장 큰 글 + 첫 쪽 첫 글, 원문 그대로)를 둔다. 파일 이름만으로
문서를 가릴 수 없을 때(input.pdf, N11.pdf) 질문 속 기관·상품·보고서 이름이 그 문서의 항목과 맞게 하려는 것이다. 근거에도
`document_label`로 실려 재정렬 후보의 문서 표시에 쓰인다. 글자 없는 문서는 파일 이름만 쓴다. 제목 추정은 모양(글자 크기·위치)만
보므로 표지가 없는 문서에서는 제목이 아닌 글이 들어갈 수 있다.

답변 값 검사(`rag/generation/answer.py`의 `cell_line`·`from_label`): 값은 근거 원문 전체이거나 원문의 이어진 일부여야 한다.
일부 인용은 숫자(부호·앞 소수점·괄호 음수·지수 포함)와 영문·하이픈으로 이어진 낱말을 자를 수 없고, 낱말 앞부분을 떼고 시작할 수
없다. 그 칸의 행·열 라벨도 값이 될 수 있으며 출력에 라벨 인용임을 밝힌다. 일부 인용은 '(원문 일부)'로 표시한다.

구조화 모델 호출(계획·재정렬·구조 검토)은 temperature 0으로 보낸다(`CallPolicy.temperature`, 추론 모델 계열은 생략).
같은 질문의 계획 문구는 여전히 조금 달라질 수 있으나 개발 세트 2회 반복에서 빗나간 문항은 같았다.

0.6이 0.5와 다른 점(셀 안 = 문장·표가 이어진 하나의 내용,
안쪽 표 = 그 내용 안의 문맥, `rag/evidence/containers.py`):
- 중복 제외: 내용을 담는 칸의 원문은 안쪽 표·칸 안 문장과 같은 글자를 이어 붙인 것이라 행·긴 셀 검색 항목과
  값 근거(`lookup_eligible`)에서 뺀다(`container_duplicate`). 칸 안 포함·덮음·읽기 순서가 모두 확정된 칸만 빼고,
  불완전한 칸은 원문을 남긴다.
- 패키지 출력과 RAG는 같은 기준으로 안쪽 표의 부모 셀을 찾는다. HTML은 DOM에 기록된 부모 셀을 사용하고 PDF는 원본 셀을 물리 표의 한 셀에 대응시킬 수 있을 때 연결한다. 검색 항목과 셀 근거에 `parent_physical_cell_id`를 기록한다.
- 안쪽 표의 검색 텍스트에는 기존 행·열 경로와 값에 부모 셀 왼쪽의 항목명을 위치 후보로 덧붙인다. HTML의 부모 셀에 있는 본문은 안쪽 표의 적용 조건으로 사용하지 않는다. 기존 색인은 해당 문서를 다시 색인할 때 갱신된다.
- 담긴 위치 문맥: 안쪽 표의 `nested_context`에 담은 칸 라벨 경로(`path`, 바깥 → 안쪽)와 바깥 칸의 앞뒤 문장
  (`outer_prose`)을 더한다. 검색 항목(`담긴 위치: …`), 리랭커(`held_in`), 답변 문맥·인용 후보(`parent_text`)에
  함께 들어간다. 무엇에 적용되는지는 판단하지 않고 모델이 원문 문맥으로 판단한다.

같은 분석 저장본에서 구조 검토로 표 배치를 다시 만들면, 입력 표의 분석 ID와 최종 검토 후보 내용으로
그 표의 검토 ID를 정한다. 같은 입력·판정은 같은 저장본 해시를 사용하며 판정이나 원문 근거가 달라지면
별도 후보가 된다. PDF를 처음부터 다시 파싱하면 원본 분석 실행 ID가 달라질 수 있다.

0.5부터: 구조 검토 후보 문서(ADR-078)는 표에 남은
`STRUCTURE_REVIEW_SCOPE` 판정을 표·행 검색 항목 첫 줄 `적용 범위: …`로 넣고, 근거에는 `scope_context`로
전달해 답변 모델이 인용할 수 있게 한다(출처 종류 `scope_context`, ID 접두어 `S`). 레이아웃이 검토로 확정된
셀은 `structure_review=layout_candidate`로 표시한다. 검토 이슈가 없는 문서의 항목은 0.4와 같다. DB 테이블 DDL과 원본
IR 계약은 바뀌지 않으며 기존 JSONB 검색 항목을 다시 만들어야 새 조각이 검색된다.
기존 `ingest --manifest ... --document ... --output ...` 명령을 같은 원본으로
실행하면 버전 차이를 감지하여 검색 항목을 트랜잭션 안에서 교체한다. 결과 출력은
새 파일 경로를 지정한다. 코드 변경만으로 기존 DB를 자동 재색인하지 않는다.
청킹 자체는 임베딩 호출이 아니다. 기본 검색은 FTS + 부분 문자열이며 벡터 모드는 별도로 선택한다.

## pgvector 설치와 임베딩

[ADR-077](ADR/077-hybrid-rag-embeddings.md)은 저장 버전·검색 결합·실패 처리의 결정을 설명한다.
기본 `compose.yaml`은 PostgreSQL 16용 `pgvector/pgvector:pg16` 이미지를 사용한다.
개발 루트에서 다음 명령은 로컬 postgres 서비스를 시작·갱신하고 기존 `postgres_data`
볼륨을 유지한 채 스키마와 확장을 설치한 뒤 벡터 연산을 확인한다. 기존 서비스의 재시작이
발생할 수 있다. 별도 `infra/vector/` 실험 DB는 이 경로에서 사용하지 않는다.

```powershell
powershell -File .\scripts\setup_rag_vector.ps1
```

이미 pgvector 지원 DB를 실행 중이면 `python -m doc_understanding.rag embedding-migrate`로
스키마만 준비할 수 있다. Docker 엔진 접근이 거부되면 사용자 터미널에서 실행해야 한다.
파일 변경·모의 테스트 통과만으로 확장 설치나 DB 마이그레이션이 완료된 것은 아니다.

기존 문서는 먼저 현재 청킹 버전으로 `ingest`한다. 이후 저장된 run ID로 임베딩한다.
공급자는 `--embedding-provider openai|local`로 고르며 CLI 기본값은 기존과 같은 openai다.
문서와 질문에는 같은 공급자·모델·차원을 사용한다. 공급자가 다르면 별도 프로필로 저장하며 벡터를 섞지 않는다.

### 로컬 임베딩 (Ollama, 비용 없음)

이 컴퓨터에서 Ollama를 실행하고 모델을 받는다. 기본 주소는 `http://127.0.0.1:11434`이며
`--embedding-base-url`은 루프백 주소(`127.0.0.1`·`localhost`·`::1`)의 http만 허용한다.
기본 모델은 다국어 `bge-m3`, 차원은 1,024다. 단가는 0으로 고정하고 외부 동의·API 키를 요구하지 않는다.
Ollama `/api/embed`에 `truncate: false`를 보내므로 모델 문맥 길이를 넘는 입력은 잘리지 않고 호출 실패로 기록된다.
태그 없는 모델명은 응답의 `:latest`만 같은 모델로 인정한다. GPU가 없으면 CPU로 실행되어 느릴 수 있다.

```powershell
ollama pull bge-m3
.\.venv\Scripts\python.exe -X utf8 -m doc_understanding.rag embed --run-id $runId --embedding-provider local --output work/manual-rag/embedding-local-01.json
.\.venv\Scripts\python.exe -X utf8 -m doc_understanding.rag search --question '질문을 입력하세요' --run-id $runId --retrieval-mode hybrid --embedding-provider local --output work/manual-rag/hybrid-local-01.json
```

### OpenAI 임베딩 (외부 전송, 유료)

`OPENAI_API_KEY`는 프로세스 환경변수에서만 읽으며 출력·감사 파일에 남기지 않는다.
아래 단가는 호출자가 공급자 요금표에서 확인해 입력한다. 기본 모델은
`text-embedding-3-small`, 차원은 1,536이다.

```powershell
$runId = Read-Host 'Stored run ID'
$embeddingRate = [double](Read-Host 'Embedding input USD per million tokens')
.\.venv\Scripts\python.exe -X utf8 -m doc_understanding.rag embed --run-id $runId --allow-external --embedding-input-usd-per-million $embeddingRate --max-embedding-cost-usd 1 --output work/manual-rag/embedding-01.json
.\.venv\Scripts\python.exe -X utf8 -m doc_understanding.rag search --question '질문을 입력하세요' --run-id $runId --retrieval-mode hybrid --allow-external --embedding-input-usd-per-million $embeddingRate --output work/manual-rag/hybrid-01.json
```

`embed`는 공급자와 관계없이 검색 텍스트를 최대 32개씩 보내며, 빈 항목이나 7,500 UTF-8 바이트를 넘는
항목은 자르지 않고 `skipped`에 기록한다. 표 개요·행·본문·셀 조각 모두 대상이며 긴 행과
문맥이 많은 조각은 제외될 수 있다. `coverage_complete`와 건너뛴 항목을 확인한다.
모델·차원·프로필 버전·입력 표현 버전과 SHA256이 같은 항목은 재사용한다. API를 부르기 전에 **다른 실행**에
같은 프로필·같은 입력 원문의 벡터가 있으면 이 실행 항목으로 복사한다(`copied_from_other_runs`). 같은 문서를
다시 적재하거나 구조 검토 후보로 새 실행을 만들어도, 문서끼리 같은 문구가 있어도 중복 임베딩하지 않는다.
완료 배치는 트랜잭션으로 저장하므로 중간 실패 후 같은 명령을 새 출력 경로로 실행하면
완료 항목을 건너뛴다. 각 명령 실행은 새 비용·호출 한도를 사용한다. CLI 호출 한도 기본값은 64회
(약 2,048항목)이며 `--max-embedding-calls`로 바꾼다. 웹 화면의 로컬 임베딩은 1,000회 한도를 사용한다.

`--embedding-profile-version`은 운영자가 지정하는 재색인 세대이며 공급자 모델의
(로컬 Ollama 모델의 가중치 갱신 포함)
불변 스냅샷을 보장하지 않는다. 모델·차원·세대를 바꾸면 별도 프로필로 저장한다.
같은 실행의 다른 프로필은 보존하되, 원본 검색 항목의 재색인 삭제 시 연결 벡터는
FK cascade로 무효화한다. 원문·IR은 삭제하지 않는다. 실제 사용량이 응답에 없으면
비용 완전성을 false로 기록하고 예약 예산을 별도로 남긴다. 자동 API 재시도는 없다.

벡터 검색 문장은 병렬 작업자 수를 정해 실행한다(`retrieval/dense.py`의 `serial_query`, 환경변수
`NH_VECTOR_SEARCH_WORKERS`, 기본 2, 0이면 병렬 없음). 검색 항목이 3만 개를 넘자 PostgreSQL이 정확 검색을 병렬로
실행했고, 컨테이너 공유 메모리(기본 64MB)가 모자라 문장이 실패했다(SQLSTATE 53100, 2026-11-13). 그래서
`compose.yaml`이 `shm_size`를 1GB로 둔다. 이 설정은 컨테이너를 다시 만들어야 적용된다(`docker compose up -d postgres`,
데이터 볼륨은 그대로). 예전 컨테이너처럼 공유 메모리가 모자라 실패하면 병렬 없이 한 번 다시 실행한다.
결과는 병렬 여부와 무관하다. 측정(문서 112개, 검색 항목 3.4만 개, 검색어 5개): 벡터 검색 4.6초(병렬 없음) → 1.1초
(작업자 2), 작업자 4는 더 빨라지지 않았다. 임베딩 호출과 키워드 검색을 합친 질문 한 건의 검색은 약 7초 → 약 3초다.
문서가 훨씬 늘면 정확 검색 자체가 한계라 근사 검색 인덱스가 필요하다(미적용).

`ask`에도 같은 `--retrieval-mode`, 임베딩 모델·단가·한도
옵션을 전달할 수 있다. 생성 모델 비용 한도와 임베딩 비용 한도는 별개다.
검색 모드가 lexical이면 임베딩 클라이언트나 API를 사용하지 않는다.

## 하이브리드 검색 결과와 한계

키워드 검색과 근거 정렬은 한글 낱말의 붙여 쓴 표기와 음절 사이에 공백이 하나씩 있는 표기를 같은 검색어로 계산한다.
비교 대상 문서마다 질문이 지목한 행이 구조 미확정 표 하나에만 있으면 해당 문서의 키워드 검색으로 원래 행 항목을 확인한다.
두 문서에서 같은 행을 찾으면 각 표의 원문 격자를 읽고, 답 칸과 그 칸에 맞닿은 행·열 라벨을 검사한다.
질문과 검색어 양쪽에서 확인한 낱말로 행 이름 전체를 구성할 수 있어도 읽기 후보가 된다. 같은 문서에서 두 행이 맞으면 이 경로로 결정하지 않는다.
이 비교 경로는 질문에 명시된 값의 연도를 각 문서의 인용 열에서 확인한다. 문서 이름·발행연도에 해당하는 범위 조건은 문서 정보와 대조한다.
열에서 연도를 확인하지 못하면 답을 보류한다. 최종 표시에는 각 값의 문서·쪽·행·열을 붙이고, 해당 표의 단위 문맥이 퍼센트만 명시하면 숫자에 %를 붙인다.
여러 단위가 함께 있으면 표의 원문 단위 표기를 함께 표시한다. 이 검사는 문서 간 같은 행을 묻는 비교에 적용하며, 지표의 의미 동등성이나 환산을 보장하지 않는다.

키워드와 벡터 검색은 동일한 완료 문서 run 목록을 사용한다. 모델·차원·입력 텍스트·
인덱스 버전이 맞는 벡터만 검색하고, 우선 근사 인덱스 없이 코사인 정확 검색을 기준선으로 둔다.
각 검색에서 최종 한도의 최대 3배(최대 30개)를 후보로 받아 `1 / (60 + 순위)`를 합산한다.
동일 run·entry 후보는 합치고 입력 근거 payload는 바꾸지 않는다. 후보의 `retrieval` 필드에
각 방식의 순위·원점수를 기록한다. RRF 점수는 정답 확률이 아니다.

벡터가 0개인 hybrid 검색은 `lexical_only_no_embeddings`로 표시하여 키워드 결과를 반환한다.
dense 검색은 이 경우 실패한다. 벡터가 일부만 있으면 coverage에 total·embedded 수를 기록한다.
DB·API 오류를 벡터 검색 성공으로 대체하지 않는다. `retrieval-audit.json`에는 실제 검색 방식,
적용 run 목록·커버리지·임베딩 호출·비용 기록이 남는다. search 명령은 출력 JSON 옆의
`*.retrieval-audit.json`, ask 명령은 결과 폴더 안에 저장한다.
LangGraph summary의 `model_calls`는 생성·해석 호출, `embedding_calls`는 임베딩 호출이다.

검색된 여러 조각이 같은 셀을 가리킬 수 있고, 긴 입력 제외·원래 후보 한도·미해결 매핑으로
근거 누락이 생길 수 있다. ANN 성능 튜닝·재정렬·독립 정답 기반 회수율 비교는 후속 평가다.
모의 벡터 테스트는 저장·순위 결합·원문 연결 계약을 확인하며 의미 검색 성능을 입증하지 않는다.

## 질문 이해 에이전트

[ADR-079](ADR/079-question-planning-agent.md). `ask --planner` 또는 웹의 **질문 이해 에이전트**를 선택하면
기존 답변 경로 앞에 계획과 구조 일치를 더한다. 순서와 호출 수는 코드가 정한다.

1. 계획: 모델이 질문을 요구 사항(적용 범위·항목·조건·기타)과 1~4개 검색어로 나눈다. 요구 사항의
   인용 구간은 공백을 무시하고 질문에 있어야 하며, 실패하면 질문 원문 하나로 검색한다(`plan_check`).
   `answer_request`는 질문이 요구하는 답(명칭·절차·금액 등)을 검색 전에 고정한다. 답변 판단은 그 인용 구간과
   요구 문구를 그대로 포함해야 한다. 생략하거나 다른 요구로 넓히면 보류하며, 요구 해석의 의미 정확도는
   여전히 모델 판단이다. 명칭 질문의 선택 값은 원문 값·라벨 전체로 제한한다(공백 정규화 허용).
   띄어쓰기 없는 정의문을 중간에서 자르기 위해 인용 검사를 완화하지 않는다. 계획 지시문이 바뀌면 계획 캐시 키도 바뀐다.
2. 검색: 계획 검색어와 원문으로 같은 검색 방식(키워드·벡터·하이브리드)을 실행해 첫 등장 순위로 합친다.
   문서 선택에서 같은 제목의 PDF·HTML이 겹치면 `agentic/publications.py`가 기존 저장본의 발행처,
   출처 호스트, 날짜가 있는 발표 머리말과 HTML 기사 본문을 PDF 원문에 대조한다. 모두 확인된 경우 두 실행을
   함께 조회하며 인용은 각 원본 ID를 유지한다. PDF의 부록·각주와 웹의 탐색 메뉴·첨부 링크는 형식 차이로
   다룬다. 본문 변경, 다른 발표 머리말, 확인할 수 없는 출처, 한도 초과는 계속 문서 선택을 요구한다.
   제목만으로 묶거나 저장본을 합치지 않으며, 이 검사는 재적재가 필요 없다.
3. 구조 일치(`rag/agentic/tools.py`, `matching.py`): 상위 표 5개에서 항목·조건 문구를 답변 가능 셀의 행·열
   라벨과 층별로 비교한다. 형식 정규화(NFKC·물결표·대시·공백) 후 문자 포함 +1, 숫자 구간(이상·이하·초과·미만·이내·~,
   일·주·개월·년·%) 포함 +2·같은 차원 배제 −2, 라벨 임베딩 코사인 0.6 이상 +0.5~1.0(문자·구간 일치가 없을 때만).
   적용 범위 문구는 구조 검토 후보 범위·표 머리말과 비교해 ±1. 미확정 셀은 고르지 않는다. 일치한 셀을 근거 앞에
   두고 기존 근거 복원 결과로 문맥을 보충한다. 임베딩은 반대말(장점/단점)을 구분하지 못해 약한 가점으로만 쓴다.
   한자 독음(前→전 등)은 규칙 사전으로 늘리지 않고 라벨 임베딩·리랭커·답변 모델의 해석에 맡긴다.
3-1. 리랭커(선택, `rag/agentic/rerank.py`): 근거 상위 30개를 문서·쪽·적용 범위·행열 경로·값 미리보기(300자)로
   요약해 모델이 관련도 0~3을 한 번에 매긴다. 관련도 → 원래 순서로 정렬하고 `max_evidence`(기본 12)개만 답변에
   넘긴 뒤 E1..로 다시 번호를 매긴다. 후보에 없는 ID·중복은 무시하고, 점수가 빠진 후보는 0.5로 본다.
   호출 실패·예산 초과면 원래 순서를 쓴다. 근거 원문·값은 바꾸지 않는다. `/ask`는 gpt-4.1-mini로 켠다.
   답변 요구가 있는 계획에서는 상위 본문 3개의 같은 쪽 앞뒤 2개 내용을 읽어 최대 8개 근거를 보충한다.
   정의·명칭이 다음 줄에 분리된 경우를 위한 읽기 보충이며, 각 내용의 원문·출처·ID를 따로 보존한다.
   인접하다는 이유로 동일한 적용 범위라고 판정하지 않는다. 저장 항목과 검색 문자열은 바꾸지 않는다.
   본문이 속한 저장된 section 후보와 부모 section을 따라 제목 원문도 `scope_context`로 전달한다.
   제목의 content ID·원문·출처가 확인된 경우만 추가하며, 제목 자신의 쪽·좌표를 인용한다.
   예를 들어 제외 사유 목록은 ‘지원제외’ 제목과 함께 전달된다. 연결이 없는 문서에서는 제목을 추측하지 않는다.
4. 답변: 기존 `generate_answer`와 인용 검사를 쓴다. 명시적인 미충족 요구가 있으면 그 요구에서 만든
   **새 검색어만 한 번** 조회한다. 원래 질문·계획 검색어를 다시 실행하지 않는다. 외부 확인·질문 모호성·
   인용 계약 오류는 검색으로 고치려 하지 않는다. 새 원본/문맥이 없으면 재정렬과 답변 호출을 멈춘다.
   새 근거가 있어도 미충족 요구를 포함한 질문으로 재정렬해 관련도 2 이상인 새 근거가 선택돼야 다시 답한다.
   재정렬이 꺼져 있거나 실패하면 관련성 미확인으로 중단한다. 기존 근거와 연결된 보류 결과는 그대로 보존한다.
   표 넓히기도 미충족 요구가 있고 실제 원본/문맥이 추가된 경우만 다시 답한다. 요청 한도를 넘으면 이미 낸
   보류를 유지하며 같은 좁은 근거로 재호출하지 않는다. 중단 원인은 `trace.retry`·`trace.recovery`에 남는다.

계획 호출은 답변과 같은 모델·단가를 쓰고 비용 한도는 호출별이다. `agent-run.json`에 계획·검색어·
후보 표·구조 일치·근거 ID·재검색이 남는다.

`--langfuse-config infra/langfuse/client.env.local`(웹은 이 파일이 있으면 자동)을 주면 실행 전체가 Langfuse
trace 하나(`nh-table-rag`, mode `question_agent`)로 남는다. 단계 span `agent.plan`·`agent.search`·
`agent.structure_match`·`agent.rerank`와, 모든 모델 호출의 generation `model.question_plan`(계획)·`model.rerank`(리랭커)·`model.embedding`
(문서·질문 임베딩, 입력은 해시만)·`document.answer`(답변)가 시작·종료 시각, 모델, 토큰, 추정 비용과 함께
기록된다. 구조 검토 에이전트의 모델 선택·Judge도 활성 trace가 있으면 `model.structure_selection`·
`model.structure_judgment`로 남는다. 내보내는 값은 기존 허용 목록·마스킹을 거치며 문서 원문은 보내지 않는다.
추적 실패는 실행을 막지 않고 `trace_warnings`에 남는다. 계획 통과·구조 일치·리랭커 관련도는 모델·규칙 후보이며
의미 정확도 승인이 아니다.

```powershell
.venv/Scripts/python.exe -X utf8 -m doc_understanding.rag ask --planner --question '질문' --run-id $runId --allow-external --input-usd-per-million 2 --output-usd-per-million 8 --output work/manual-rag/agent-01
```

## 범용 질문과 근거 판단

모델 지시문은 `rag/prompts/`에서 관리한다. `understanding.py`는 검색 계획,
`selection.py`는 근거 선택형 답변, `narrative.py`는 서술형 답변을 지시한다.
두 답변 지시문은 `prompts/assessment.py`의 공통 요구 사항 판단 지시문을 조합한다.
모델 호출은 `generation/`, 응답 스키마와 질문·원문 인용 검사는
`evidence/assessment.py`에 남는다. 프롬프트 변경은 검증 코드 변경과 구분하여 평가한다.
지시문의 실제 요청 내용은 각 실행의 `request.json`에서 확인할 수 있다.

[ADR-076](ADR/076-generic-question-assessment.md)은 판단과 원문 검사 분리의 결정·한계를 설명한다.

수치·기간·조건·최신성 질문을 고정 단어 목록으로 분류하지 않는다. 사전 검사는
근거 ID, 원문 존재, 표 셀 매핑의 사용 가능 여부와 명시적 출처 제약만 검사한다.
`validation.sufficient`는 모델 호출을 진행할 수 있다는 뜻이며, 질문에 답할 수 있다는
의미가 아니다. `scope=structural_preflight_only`, `question_coverage=not_assessed`로 표시한다.

기본/Agent/문장형 모두 기존 답변 모델 호출에서 질문의 요구 사항과 답변을 함께 만든다.
각 요구 사항은 질문 원문의 인용 구간, 해석, supported/unsupported/ambiguous 판단과
원문 source_id·필드·인용을 포함한다. 모델이 조건을 누락하거나 의미를 잘못 해석할 수
있으므로 이 결과는 모델 후보이며 별도 독립 평가나 사람 승인이 아니다.

코드는 요구 사항의 질문 인용, 출처 ID, 원문 인용, 선택 근거 연결, 값 보존을 검사한다.
불충분·모호·외부 확인 필요 판단 또는 인용 오류는 답변 보류로 이어진다.
표의 텍스트 값과 본문의 숫자를 모두 허용하고, 미해결 표 매핑은 계속 차단한다.
행·열 라벨과 표 머리말, 단위, 주석, 부모 셀 본문을 함께 전달하며 문맥은 셀별 연결을 보존한다.
문장형 답변에서는 판단에 사용한 출처를 실제 답변에서도 인용해야 하고 조건·예외의
원문 절을 보존해야 한다. 단어 사전으로 적용 범위나 의미적 함의를 인증하지 않는다.

선택형 모델 응답에는 `assessment`가 필수로 추가되었고 문장형에도 같은 계약이 적용된다.
이전 저장 응답은 새 계약을 충족하지 않는다. 반환되는 `selection` 구조는 유지한다.
답변 기본 출력 한도는 2,400토큰이며 요청 크기·비용 한도와 외부 호출 허용 조건은 유지한다.
추가 검토 모델을 자동 호출하지 않는다. `--agent`의 재작성 호출은 별도다.

## 평가 기준의 버전과 동등 표현

`rag-general-v2.json`과 `rag-holdout-v2.json`은 기존 질문·기대 답·기본 근거 위치를 유지하고,
명시된 동등 표현과 근거 위치만 추가한다. v1 설정·실행 결과·점수는 덮어쓰지 않는다.
지표 버전은 `rag/5-explicit-equivalences`이며 실행별 설정과 스냅샷을 함께 보관한다.

`expected_equivalents`는 지정된 기대 표현의 대체 표현만 허용한다. 예를 들어 c-01의
`2,500 billion`과 `$2.5 trillion`을 인정하되 다른 단위·음수·더 큰 숫자의 부분 일치는
인정하지 않는다. 자동 환산이나 질문 요구 완화는 하지 않는다. 동등 표현이 없는 v1 항목의
문자열 판정은 그대로다.

`gold[].equivalent_locations`는 같은 문서 안에서 같은 사실을 나타내는 대체 위치다.
각 필수 근거 그룹 안에만 추가하므로 비교 질문에서 필요한 다른 문서의 근거를 대신하지
못한다. 다른 문서 지정은 거절하고, 행 라벨이 지정된 위치는 기존 행 제한을 유지한다.
c-01은 동등 금액 문장이 있는 BIS 본문, g-20은 같은 신한 문서의 최저가입금액 행을
추가로 인정한다. c-01은 선택한 출처도 해당 근거 그룹에 포함되어야 한다.
이 설정은 개발용 평가 기준이며 사람 검증된 금융 사실을 발행하지 않는다.

## 현재 한계

- 매핑되지 않은 원본 셀의 검색 포함은 보장하지 않는다.
- 셀 본문과 경로를 함께 정렬한다. 문서당 기본 8셀 한도는 설정 가능하며 한도 밖
  근거가 제외될 수 있다.
- 본문·주석 등의 추가 근거는 별도이며 모든 복합표 관계가 완성된 것은 아니다.
- 모델의 요구 사항 분해·의미 판단이 틀릴 수 있다. 정확한 인용과 조건별 판단 기록이
  있어도 의미적 함의나 질문의 모든 조건을 빠짐없이 해석했다는 증거는 아니다.
- 상대 기간의 기준 시점이나 문서 밖 현재 유효성을 입증할 근거가 없으면 모델이
  모호함/외부 확인 필요로 분류해야 한다. 이를 규칙 기반 정답 판정으로 보장하지 않는다.
- 모의 응답 회귀는 계약과 보류 동작을 검증한다. 범용 성능은 미사용 문서·질문과
  사람의 정답 근거를 사용한 실제 모델 평가가 별도로 필요하다.
- Tree 구조는 의미 검증 전 후보다. 범용 질문 해석·검색 성능 개선은 별도 작업이다.
